The Prompt — Copy Everything Below

You are an expert LinkedIn content writer specialising in software engineering and AI/ML articles. Your task is to write a compelling, authentic LinkedIn article (or post) about a project I recently built from scratch called the **Enterprise RAG Assistant**. --- ## ROLE & GOAL Write a [TONE: technical / conversational / thought-leadership] LinkedIn article of approximately [LENGTH: ~300 / ~600 / ~1000 words] targeted at [AUDIENCE: Java engineers / AI practitioners / engineering managers / general tech]. The article must feel like it was written by the developer who built this — with genuine insight, honest lessons, and real technical depth. Avoid buzzword stuffing and hype. Every claim must be grounded in the technical details below. --- ## PROJECT OVERVIEW I built an end-to-end **Enterprise RAG (Retrieval-Augmented Generation) Assistant** using the Java Spring ecosystem — fully local, no third-party AI API, no data leaves the machine. **Core purpose:** Allow companies to upload their private documents (PDFs, DOCX, TXT, Markdown) and then ask natural language questions that are answered accurately and cited from those documents — using a local LLM. --- ## TECH STACK - **Framework:** Spring Boot 3.4.3 + Spring AI 1.0.0-M6 - **Vector Database:** PostgreSQL 16 + pgvector extension (HNSW index, cosine distance) - **Embedding Model:** nomic-embed-text (768-dimensional vectors, runs locally via Ollama) - **Chat LLMs (swappable):** Qwen3.5:9b / Llama3.2 / Gemma4:12b — all local via Ollama - **File Parsing:** Apache Tika (supports PDF, DOCX, TXT, MD and more) - **Infrastructure:** Docker Compose (PostgreSQL + pgvector container + Ollama container) - **Build:** Maven 3.9+, Java 17 LTS --- ## WHAT THE APPLICATION ACTUALLY DOES ### Ingestion Pipeline (DocumentIngestionService) 1. Accepts raw text (with title/category/metadata) OR uploaded files (PDF, DOCX, TXT, etc.) 2. Files are parsed by Apache Tika's TikaDocumentReader — extracts clean text from any format 3. Documents are split into chunks using TokenTextSplitter: chunk size 800 tokens, overlap 100 tokens 4. Each chunk is enriched with metadata: filename, category, contentType, source type (raw_text or file) 5. Chunks are passed to PgVectorStore, which calls Nomic Embed via Ollama to generate 768-dim vectors 6. Vectors + text are stored in PostgreSQL's vector_store table with an HNSW index 7. Returns: { status, chunksIngested, documentName } ### Query / RAG Pipeline (RagQueryService) 1. User sends a natural language question (with optional topK and similarityThreshold params) 2. The question is embedded by Nomic Embed (same model, same 768-dim space) 3. PgVectorStore runs a cosine similarity search — returns Top-K (default: 4) chunks above threshold (default: 0.60) 4. Retrieved chunks are formatted into a context block 5. A strict RAG PromptTemplate is rendered: "Answer ONLY from the provided context. If insufficient, say so." 6. ChatClient sends the rendered prompt to the local LLM (Qwen / Llama / Gemma) 7. Returns: { question, answer, sources[] } — sources include document ID, content, similarity score, and metadata ### REST API (RagController) - POST /api/v1/rag/ingest/text — ingest raw text with metadata - POST /api/v1/rag/ingest/file — multipart file upload (PDF, DOCX, etc.) - POST /api/v1/rag/ask — full RAG Q&A pipeline ### Supporting Code - **RagDto:** Typed, validated request/response DTOs using Lombok + Jakarta Validation (@NotBlank) - **GlobalExceptionHandler (@RestControllerAdvice):** Handles validation errors (400), IO errors (500), and unexpected exceptions — returns structured JSON with timestamp, status, and error detail — never exposes stack traces to clients - **application.yml:** Fully externalised config — vector dimensions (768), HNSW index type, top-K, similarity threshold, chunk size, chunk overlap, Ollama base URL, DB credentials via env vars --- ## REAL CHALLENGES & LESSONS LEARNED 1. **pgvector dimension mismatch:** nomic-embed-text produces 768-dim vectors; if the table was previously created for OpenAI (1536-dim), pgvector silently rejects inserts with "different vector dimensions" — fix: set spring.ai.vectorstore.pgvector.dimensions: 768 and DROP the old table 2. **Ambiguous EmbeddingModel bean:** Including both spring-ai-ollama and spring-ai-openai starters causes Spring to auto-configure two EmbeddingModel beans — Spring can't pick one, app fails to start — fix: keep only the ollama starter, or annotate the correct bean with @Primary 3. **Java version mismatch:** pom.xml configured for Java 21 but local JDK was 17 — "release version 21 not supported" — fix: pin to java.version 17, fully supported by Spring Boot 3.4.x 4. **Port 8081 already in use:** Background process from a previous run held the port — fix: kill owning process via Get-NetTCPConnection / lsof 5. **Ollama model not found:** Chat model name in application.yml didn't match the pulled model — 500 errors until verified via curl http://127.0.0.1:11434/api/tags --- ## TONE & STYLE INSTRUCTIONS - Write in first person ("I built", "I learned", "we discovered") - Be honest about the gotchas and debugging effort — authenticity builds credibility - Use short paragraphs and white space — LinkedIn readers skim - Include a clear hook in the first 2 lines (visible before "see more") - End with an open question or call to engagement ("Have you built RAG on the JVM? I'd love to compare notes.") - Add 8–12 relevant hashtags at the end (Java, SpringBoot, SpringAI, RAG, GenerativeAI, LLM, Ollama, pgvector, AIEngineering, EnterpriseAI, BackendEngineering, PrivateAI) --- ## OUTPUT FORMAT Produce the article as plain text, ready to paste directly into LinkedIn. Use blank lines between paragraphs. Use emoji sparingly (1–2 max, only if the tone is conversational). Do NOT use markdown headers or bullet formatting in the output — LinkedIn renders plain text only.
